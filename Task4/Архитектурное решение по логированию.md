# Архитектурное решение по логированию и трейсингу


## 1. Мотивация

### Проблемы:

* Отсутствие прозрачности: Невозможно отследить путь заказа через систему.
* Долгий разбор инцидентов: Поддержка тратит часы на воспроизведение ошибок со слов клиентов.
* Потеря данных: Сообщения теряются в очередях, заказы зависают в непонятных состояниях.
* Ручная диагностика: Разработчики анализируют логи вручную, без автоматизации.

### Цели:

* Сократить время диагностики проблем на 80%.
* Автоматизировать обнаружение аномалий (например, DDoS, зависшие заказы).
* Повысить SLA обработки заказов до 98%.
* Уменьшить количество обращений в поддержку на 80%.

## 2. Необходимые логи

### Ключевые системы для сбора:

#### 1. Shop API (уровень INFO/ERROR):

* События: order_created, order_updated, payment_processed.
* Данные: order_id, user_id, timestamp, status, error_code (если есть), error_message (если есть).
* Пример:
```json
{
  "level": "INFO",
  "timestamp": "2026-02-02T11:12:00Z",
  "service": "Shop API",
  "event": "order_created",
  "order_id": "ORD-xxx",
  "user_id": "USER-xxx",
  "status": "pending",
  "error_message": "не поступили данные, проверьте соединение"
}
```

Также я бы логировал успешные события, но коротко и четко, с указанием order_id и конкретным типом операции.

#### 1. CRM (уровень INFO):

* События: client_updated, ticket_opened, notification_sent.
* Данные: client_id, action, metadata.

#### 1. MES (уровень INFO/ERROR):

* События: production_started, production_failed, cost_calculated.
* Данные: order_id, operator_id, machine_id, error_details.

#### 1. Messages Queue (уровень WARNING):

* События: message_delayed, message_lost, queue_overload.

### Уровни логирования:

* `DEBUG`: Для отладки сложных кейсов (включается только по запросу).
* `WARNING`: Задержки в очереди, частичные сбои (не критические).
* `ERROR`: Критические ошибки (например, потеря связи с БД).
* `FATAL`: Полный отказ сервиса.

## 3. Трейсинг

### Компоненты для покрытия:

* Shop API
* CRM API
* MES API
* Messages Queue
* 3D Storage

### Данные для трейсов:

* `trace_id` (уникальный идентификатор цепочки запросов).
* `span_id` (идентификатор этапа обработки).
* Временные метки начала/окончания этапа.
* Статус (успех/ошибка).
* Контекстные данные: `order_id`, `user_id`.
* Пример трейса:
```json
{
  "trace_id": "TRACE-TEST-123",
  "spans": [
    {
      "span_id": "SPAN-1",
      "service": "Shop API",
      "start_time": "2025-20-02T11:45:00Z",
      "end_time": "2025-20-02T11:45:02Z",
      "status": "success",
      "metadata": {"order_id": "ORD-123"}
    },
    {
      "span_id": "SPAN-2",
      "service": "CRM API",
      "start_time": "2025-20-02T11:45:03Z",
      "end_time": "2025-20-02T11:45:05Z",
      "status": "error",
      "error": "Database connection timeout"
    }
  ]
}
```

## 4. Предлагаемое решение

### Технологический стек:
| Комментарий  | Технологии                                  | Назначение                                            |
| ------------ | ------------------------------------------- | ----------------------------------------------------- |
| Логирование  | ELK Stack (Elasticsearch, Logstash, Kibana) | Централизованный сбор, хранение и визуализация логов. |
| Трейсинг     | Jaeger + OpenTelemetry                      | Трассировка запросов между сервисами.                 |
| Мониторинг   | Prometheus + Grafana                        | Сбор метрик и алертинг.                               |
| Безопасность | Vault + TLS v1.2                            | Шифрование логов и управление секретами.              |

### Интеграция:

#### 1. Агенты сбора:

* Filebeat на каждом сервисе для отправки логов в Logstash.
* OpenTelemetry SDK для генерации трейсов.

#### 2. Центральный кластер:

* Elasticsearch для логов, Jaeger для трейсов.

#### 3. Визуализация:

* Kibana для логов, Grafana для метрик и алертов.

## 5. Политики

### Безопасность:

* Шифрование: Все логи и трейсы шифруются при передаче (TLS) и хранении.
* Доступ:
* * Поддержка: Только просмотр логов уровня INFO/ERROR.
* * Разработчики: Доступ к DEBUG-логам и трейсам.
* * Администраторы: Полный доступ + управление политиками.
* Маскирование данных:
* * Поля user_id, email заменяются на хэши перед сохранением.

### Хранение:

* Логи:
* * INFO — 30 дней.
* * ERROR/FATAL — 1 год.
* Трейсы:
* * Хранятся 14 дней (для анализа SLA).
* * Агрегированные метрики (например, среднее время обработки) — 1 год.

## 6. Автоматизация и алертинг

### Метрики для алертов:

* Зависшие заказы:
* * Если заказ не меняет статус более 1 часа → алерт в Slack/Telegram.
* Аномальная активность:
* * Резкий рост ошибок в CRM API (более 5% за 5 минут) → алерт + автосоздание тикета.
* Потеря сообщений:
* * Более 10 сообщений потеряно в очереди за час → алерт.

### Интеграция с мониторингом:

* Prometheus собирает метрики из логов (через Logstash Exporter).
* Grafana дашборды:
* * Технические: Время ответа сервисов, нагрузка на БД.
* * Бизнес-метрики: Конверсия заказов, среднее время обработки.


## 7. Компромиссы

* Производительность:
* * Трейсинг добавляет задержку ~3-5 мс на запрос. Решение: использовать sampling (собирать 10% трейсов).
* * Трейсинг можно настроить через фиче флаг и тот же FeatBeat для управления, позволит включать и отключать трейсинг на ходу.
* Legacy-системы:
* * MES на .NET Framework не поддерживает OpenTelemetry. Решение: написать обертку для логирования.
* Стоимость:
* * ELK требует 3 ноды для кластера → минимум $500/мес. Альтернатива: использовать OpenSearch с managed-хостингом.


## 8. Критерии выбора технологий

| Критерий         | ELK                           | OpenSearch                    |
| ---------------- | ----------------------------- | ----------------------------- |
| Стоимость        | Бесплатно (Community Edition) | Бесплатно (Apache 2.0)        |
| Масштабируемость | Подходит для средних нагрузок | Аналогично ELK                |
| Интеграции       | Широкая поддержка фреймворков | Совместим с Elasticsearch API |
| Безопасность     | RBAC, шифрование              | RBAC через плагины            |
| Сообщество       | Активное                      | Растущее                      |

#### Выбор: ELK + OpenTelemetry + Jaeger. Причины:

* Бесплатные решения с открытым кодом.
* Гибкая интеграция с микросервисами.
* Поддержка Kubernetes (актуально для будущего масштабирования).
