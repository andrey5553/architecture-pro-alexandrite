Задание 2. Мониторинг

Выбор и настройка мониторинга в системе
    1. Мотивация

    Внедрение мониторинга в систему компании «Александрит» необходимо для решения следующих задач:
        1.1 получение полной картины работы системы после внедрения API;
        1.2 выявление «бутылочных горлышек» в процессах обработки заказов;
        1.3 оптимизация взаимодействия между компонентами системы (онлайн-магазин, CRM, MES);
        1.4 сокращение времени обработки заказов и повышение удовлетворённости клиентов;
        1.5 обеспечение стабильной работы системы при растущей нагрузке;
        1.6 своевременное выявление и устранение технических проблем и ошибок;
        1.7 также стоит добавить логирование в контроллеры или хендлеры с расчетом времени работы событий;
        1.8 алерты позволят видеть картину происходящего в постоянном режиме;


    Мониторинг упростит поиск возникающих проблем, принимать оперативно действия для устранения,  оптимизировать рабочие процессы. 
    Это, в свою очередь, приведёт к улучшению качества обслуживания клиентов, 
    повышению эффективности работы сотрудников и росту прибыли компании, а также повысит репутацию компании.

    2. Выбор подхода к мониторингу
    Для мониторинга системы компании «Александрит» предлагается использовать комбинацию подходов:
        2.1 RED ((Rate) Requests, Errors, Duration) для онлайн-магазина и CRM. 
        Этот подход позволит отслеживать основные метрики, связанные с обработкой запросов, ошибками и временем обработки. Там где есть бизнес логика. 
        2.2 USE (Utilization, Saturation, Errors) для MES. 
        Этот подход лучше подходит для мониторинга системных метрик, таких как загрузка процессора, памяти, дискового пространства, а также ошибок и активности пользователей.

    3. Метрики для отслеживания
    Онлайн-магазин:
        * Количество запросов (Requests).
            Зачем нужна метрика: для оценки нагрузки на онлайн-магазин и выявления периодов пиковой активности. Или наоборот отслеживания падения кол-ва запросов.
            Ярлыки: время суток, день недели, тип запроса (просмотр товара, загрузка 3D-модели, оформление заказа).
        * Процент ошибок (Errors) (500-х или 400-х ошибки).
            Зачем нужна метрика: для выявления и устранения проблем, приводящих к ошибкам в работе онлайн-магазина.
            Ярлыки: тип ошибки (клиентская, серверная), страница, на которой возникла ошибка.
        * Время обработки запросов (Duration).
            Зачем нужна метрика: для оценки времени, затрачиваемого на обработку запросов пользователей, и выявления «узких мест».
            Ярлыки: тип запроса (просмотр товара, загрузка 3D-модели, оформление заказа), время суток. Я бы добавил наличия логов с учетом времени выполнения или падения работы в апи.
    CRM:
        * Количество запросов к API (Requests).
            Зачем нужна метрика: для оценки нагрузки на CRM и выявления периодов пиковой активности продавцов.
            Ярлыки: тип запроса (управление клиентами, заказами), время суток, день недели.
        * Процент ошибок в API (Errors).
            Зачем нужна метрика: для выявления проблем, влияющих на работу продавцов в CRM.
            Ярлыки: тип ошибки, API-метод, в котором возникла ошибка.
        * Время обработки запросов (Duration).
            Зачем нужна метрика: для оценки времени, затрачиваемого на обработку запросов продавцов, и оптимизации работы CRM.
            Ярлыки: тип запроса, время суток.
    MES:
        * Загрузка CPU и памяти (System).
            Зачем нужна метрика: для отслеживания использования ресурсов сервера MES и выявления периодов высокой нагрузки.
            Ярлыки: время суток, день недели.
        * Количество активных пользователей (User).
            Зачем нужна метрика: для оценки количества операторов, одновременно работающих с MES.
            Ярлыки: время суток, день недели.
        * Процент ошибок (Errors).
            Зачем нужна метрика: для выявления технических проблем, влияющих на работу MES.
            Ярлыки: тип ошибки, компонент MES, в котором возникла ошибка.
        * Время расчёта стоимости заказа (Custom metric).
            Зачем нужна метрика: для оценки времени, затрачиваемого MES на расчёт стоимости заказа, и оптимизации алгоритмов расчёта.
            Ярлыки: сложность 3D-модели (количество полигонов), тип материала.
        * Время загрузки списка заказов (Custom metric).
            Зачем нужна метрика: для оценки времени, затрачиваемого на загрузку списка заказов в MES, и оптимизации отображения данных.
            Ярлыки: количество заказов в системе, фильтры и параметры отображения.
    Очередь сообщений (RabbitMQ):
        * Количество сообщений в очереди (Queue length).
            Зачем нужна метрика: для отслеживания количества сообщений в очереди и выявления задержек в обработке заказов.
            Ярлыки: тема сообщения (new orders, status changes), время суток.
        * Время доставки сообщений (Delivery time).
            Зачем нужна метрика: для оценки времени доставки сообщений между компонентами системы и выявления задержек.
            Ярлыки: тема сообщения, отправитель, получатель.
        * Время обработки сообщений.
            Зачем нужна метрика: для оценки времени обработки сообщений и выявления задержек.
            Ярлыки: тема сообщения, отправитель, получатель.
    Хранилище 3D-файлов:
        * Объём используемого хранилища (Storage usage).
            Зачем нужна метрика: для отслеживания объёма используемых данных и планирования масштабирования хранилища.
            Ярлыки: тип файлов (3D-модели, конструкторские элементы), период времени.
        * Время загрузки/выгрузки файлов (File I/O time).
            Зачем нужна метрика: для оценки времени загрузки и выгрузки 3D-файлов и оптимизации работы с хранилищем.
            Ярлыки: размер файла, тип операции (загрузка, выгрузка).
    Дополнительные метрики:
        * Время отклика API (API response time).
            Зачем нужна метрика: для оценки времени отклика API, используемого внешними клиентами, и оптимизации взаимодействия с ними.
            Ярлыки: тип API-запроса, источник запроса (внешние клиенты, внутренние системы).

    4. План действий
    Задача 1: создать инфраструктуру для сбора и хранения метрик.
        Действия: развернуть time-series базу данных (например, Prometheus) для хранения метрик мониторинга.
        Сроки: 2 недели.
    Задача 2: настроить сбор метрик с компонентов системы.
        Действия: установить агенты мониторинга на серверы онлайн-магазина, CRM, MES; настроить экспорт метрик из RabbitMQ и хранилища 3D-файлов;
            разработать скрипты для сбора дополнительных метрик (например, статусы заказов, время отклика API).
        Сроки: 4 недели.
    Задача 3: настроить визуализацию и анализ метрик.
        Действия: развернуть систему визуализации метрик (например, Grafana);
            создать дашборды для отображения ключевых метрик по каждому компоненту системы;
            настроить панели мониторинга для разных ролей (разработчики, операторы, менеджеры, девопсы, служба тех поддержки).
        Сроки: 4 недели.
    Задача 4: определить пороговые значения метрик и настроить оповещения.
        Действия: установить пороговые значения для ключевых метрик;
            настроить систему оповещений (например, через Slack, matermost или email) при превышении пороговых значений.
        Сроки: 2 недели.
    Задача 5: разработать процедуры реагирования на превышения пороговых значений.
        Действия:  описать шаги по устранению проблем для каждой критической ситуации (например, высокая загрузка CPU, большое количество ошибок, задержки в обработке заказов);
            назначить ответственных за реагирование на оповещения;
            внедрить автоматизированные процессы (например, автоматическое масштабирование ресурсов при высокой нагрузке).
        Сроки: 4 недели.
    Задача 6: провести тестирование системы мониторинга.
    Действия: смоделировать различные сценарии (пиковая нагрузка, ошибки, задержки) и проверить работу системы мониторинга;
        собрать обратную связь от команды и внести необходимые корректировки.
        Сроки: 3 недели.
    Задача 7: запустить систему мониторинга в продакшн.
        Действия: перевести систему мониторинга в режим полноценной эксплуатации.
        Сроки: после успешного тестирования.
    5. Показатели насыщенности и действия при их превышении
        Онлайн-магазин:
        Количество запросов: пороговое значение — 10 000 запросов в минуту. При превышении — отправить оповещение команде разработчиков, рассмотреть возможность горизонтального масштабирования инстансов.
        Процент ошибок: пороговое значение — 5%. При превышении — автоматически создать тикет в системе отслеживания ошибок, назначить ответственного за расследование и устранение проблемы.
        Время обработки запросов: пороговое значение — 3 секунды. При превышении — отправить оповещение DevOps-инженеру, провести анализ «узких мест», оптимизировать код или инфраструктуру.
        CRM:
        Количество запросов к API: пороговое значение — 5 000 запросов в минуту. При превышении — отправить уведомление команде, рассмотреть масштабирование API-сервисов.
        Процент ошибок в API: пороговое значение — 3%. При превышении — создать тикет, назначить разработчика для устранения проблемы.
        Время обработки запросов: пороговое значение — 2 секунды. При превышении — отправить оповещение, провести аудит и оптимизацию API.
        MES:
        Загрузка CPU: пороговое значение — 80%. При превышении — отправить оповещение, рассмотреть добавление дополнительных инстансов MES.
        Загрузка памяти: пороговое значение — 75%. При превышении — отправить уведомление, проанализировать использование памяти, оптимизировать код или добавить ресурсы.
        Количество активных пользователей: пороговое значение — 50 одновременных пользователей. При превышении — отправить оповещение, оценить необходимость масштабирования системы.
        Время расчёта стоимости заказа: пороговое значение — 30 минут для сложных моделей. При превышении — отправить уведомление разработчикам, оптимизировать алгоритмы расчёта.
        Время загрузки списка заказов: пороговое значение — 10 секунд. При превышении — отправить оповещение, оптимизировать запросы к базе данных или кэширование,
        или партиционирование.
        Очередь сообщений (RabbitMQ):
        Количество сообщений в очереди: пороговое значение — 1 000 сообщений. При превышении — отправить оповещение, проверить обработку сообщений, увеличить количество потребителей.
        Время доставки сообщений: пороговое значение — 5 секунд. При превышении — отправить уведомление, проверить настройки очереди и сетевые задержки.
        Хранилище 3D-файлов:
        Объём используемого хранилища: пороговое значение — 80% от общего объёма. При превышении — отправить оповещение, начать планирование расширения хранилища.
        Время загрузки/выгрузки файлов: пороговое значение — 20 секунд для файлов размером 100 МБ. При превышении — отправить уведомление, оптимизировать процессы ввода-вывода, проверить сетевые настройки.
