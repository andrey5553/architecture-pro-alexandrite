Планирование: анализ, идентификация проблем и поиск решений

1. Анализ схемы и описание системы
    Система ювелирного магазина «Александрит» состоит из нескольких компонентов:
        1.1 онлайн-магазин (Vue, Java Spring Boot);
        1.2 CRM (Vue, Java Spring Boot);
        1.3 MES (React, C#); (сторонний сервис, купленный. Рассчитывает стоимость производства)
        1.4 хранилище 3D-файлов;
        1.5 очереди сообщений (RabbitMQ);
        1.6 базы данных (PostgreSQL).
    Система позволяет клиентам загружать 3D-модели ювелирных изделий или создавать их с помощью конструктора, а также оформлять заказы. 
    Продавцы работают с CRM, операторы — с MES. API позволяет внешним пользователям отправлять запросы и получать данные (количество внешних пользователей растет).

2. Выявленные проблемные места:
    2.1 Задержки в обработке заказов. Клиенты жалуются на длительные сроки выполнения заказов. Несмотря на то что производственные мощности позволяют справиться с нагрузкой, заказы обрабатываются медленно.
    2.2 Проблемы с производительностью MES. Операторы сообщают о длительном времени загрузки первой страницы MES, где отображается список заказов. Фильтры и пагинация не решили проблему.
    2.3 Увеличение нагрузки на систему. С ростом числа заказов и добавлением новых клиентов через API система испытывает дополнительную нагрузку.
    2.4 Длительное время расчёта стоимости заказа в MES. Для сложных и детализированных моделей время обработки может достигать 30 минут.
    2.5 Оценка нагрузочной способности: отсутствие метрик по пиковым нагрузкам, неясность в распределении нагрузки между сервисами.
    2.6 Оценка безотказности системы: единая точка отказа, отсутствие мониторинга состояния узлов (uptime, RTO).
    2.7 Задержки релизов из-за багов. QA-инженер обнаруживает баги уровня high или highest, что приводит к задержкам в деплое на продакшн.
    
    Нарушение Single Responsibility: MES выполняет как бизнес-логику, так и расчёты стоимости, а CRM совмещает работу с клиентами и обработку заказов.
    
3. Инициативы для устранения проблем:
    3.1 Оптимизация производительности MES:
    3.1.1 провести аудит кода и базы данных MES, выявить узкие места;
    3.1.2 рассмотреть возможность масштабирования MES (например, добавить дополнительные инстансы в k8s);
    (можно внедрить разные политики работы с инстансами и тем самым снизить назрузку)
    3.1.2 подумать над партиционированием данных в БД для MES;
    3.1.3 подумать над шардированием и репликацией данных MES;
    3.1.4 оптимизировать алгоритмы обработки данных, особенно для отображения списка заказов;
    3.1.5 улучшить кэширование данных, чтобы снизить нагрузку на базу данных;
    3.1.6 настроить количественные метрики, для выявления узких мест и нагрузки;
    3.1.7 настроить систему оповещений (alerts) для оперативного решения проблем;

    3.2 Декомпозиция существующих сервисов:
    3.2.1 проанализировать границы и зависимости между сервисами (соблюдение принципа SRP);
    3.2.2 если необходимо, то выделить новые сервисы для реализации отдельной бизнес логики;
    3.2.3 понизить связность сервисов для возможности последующего горизонтального масштабирования;
    
    3.3 Улучшение процессов обработки заказов:
    3.3.1 проанализировать поток заказов и выявить «бутылочные горлышки»;
    3.3.2 поменять взаимодействие между CRM и MES а АПИ колов на брокер сообщений;
    3.3.3 внедрить дополнительные механизмы мониторинга и оповещения о задержках в обработке заказов.
    
    3.4 Масштабирование инфраструктуры:
    3.4.1 увеличить ресурсы (CPU, память, дисковое пространство) для ключевых компонентов системы (онлайн-магазин, CRM, MES);
    3.4.2 горизонтальное масштабирование (добавление дополнительных инстансов) для компонентов, испытывающих высокую нагрузку.
    
    3.5 Улучшение процесса тестирования и развёртывания:
    3.5.1 автоматизировать тестирование наиболее критичных сценариев, чтобы сократить время обнаружения багов;
    3.5.2 внедрить более строгие критерии для классификации багов, чтобы избежать необоснованных задержек в релизах;
    3.5.3 рассмотреть возможность сокращения времени цикла разработки и тестирования;
    3.5.4 возможно стоит нанять еще одного тестировавщика (на написание автотестов)
    
    3.6 Оптимизация расчёта стоимости заказа:
    3.6.1 исследовать параллельную обработку расчётов для нескольких заказов;
    3.6.2 использовать более мощные вычислительные ресурсы для расчётов стоимости;
    3.6.3 разработать алгоритмы, позволяющие ускорить обработку сложных 3D-моделей.

    3.7 Расчёт нагрузки на отдельные сервисы:
    3.7.1 внедрение системы мониторинга производительности;
    3.7.2 проведение нагрузочного тестирования;
    
    3.8 Мониторинг состояния системы:
    разбиение Shop API на ряд микросервисов, убрав единую точку отказа;
    3.8.1 регулярное автотестирование (ночные прогоны);
    3.8.2 внедрение системы мониторинга состояния компонентов (метрики, алерты, логи)
    3.8.3 в случае критичных мест системы, возможно внедрение трейсинга (на период стабилизации нагрузки)

4. Приоритет инициатив:
    4.1 Оптимизация производительности MES (исследование параллельности обработки заказов). Это критически важно, так как проблемы с MES напрямую влияют на работу операторов и, следовательно, на сроки выполнения заказов.
    4.2 Улучшение процессов обработки заказов (переход сервиса на прием сообщений, чтобы сервис не падал под нагрузкой, а имел очередь обработки). Оптимизация потока заказов поможет сократить сроки их выполнения и улучшить удовлетворённость клиентов.
    Хочу еще добавить, что можно настроить паттерн Backpressure, дабы обрабатывать заказы в нужном объеме (rabbitMQ это позволяет)
    4.3 Внедрение системы мониторинга состояния отдельных сервисов и их производительности. Позволит своевременно выявлять узкие места.
    4.4 Декомпозиция сервисов. Соблюдение принципа единой ответственности позволит уйти от единой точки отказа и мастабировать отдельно взятый функционал.
    4.5 Масштабирование инфраструктуры. Увеличение ресурсов и горизонтальное масштабирование позволят системе справляться с растущей нагрузкой.

5. Целевая архитектура через год:
    5.1 MES с улучшенной производительностью, способное быстро обрабатывать запросы операторов
    5.2 Оптимизированный поток заказов, обеспечивающий их быструю обработку и отправку клиентам
    5.3 Масштабируемая инфраструктура, способная справляться с увеличением числа заказов без потери производительности
    5.4 Ускоренный расчёт стоимости заказа, даже для сложных 3D-моделей (если будет найдена методика)
    5.5 Автотесты (контур и прогоны ночные)
    5.6 Нагручное тестирование
    5.7 Мониторинг сервиса через grafana UI дабы отслеживать аномалии

6. Три приоритетных пункта для выполнения в ближайшие полгода:
6.1 Оптимизация MES. Самая большая и важная проблема. Без решения этой проблемы операторы продолжат сталкиваться с задержками, что скажется на сроках выполнения заказов, либо ухода клиентов.
6.2 Внедрение системы мониторинга состояния отдельных сервисов и их производительности. Позволит выявлять узкие места и масштабировать отдельные сервисы при необходимости.
6.3 Масштабирование инфраструктуры. Рост нагрузки требует увеличения ресурсов системы.
